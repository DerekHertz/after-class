## Budgets

- One `Budget` serves every user, built once in `main.ts`'s `compose` on the raw `Db` in live mode and passed to each user's `createMemo` and `createLedger` in `wire`. Each memo reserves as its own `UserDb`'s user. Replay mode builds none. At boot, before any request, `reconcileInterrupted` gives every hold a previous process left unsettled a usage event of unknown cost (outcome `aborted`) and settles it at the price its response was given, or at its reservation when it has none.
- The choke point is the request site. `AttemptContext` is a `SendContext` (`signal`, `admit`) plus `streamTo`, and `ClaudeCli` takes a `SendContext` in place of a signal. Each adapter calls `admit()` immediately before a request leaves: the API adapter in `call()` after its concurrency slot is granted (so once per resource-search continuation), the CLI adapter just before spawning, each Jev task just before `jev.ask`. `admit` reserves one hold per request and throws `BudgetHeld` when refused. `unbudgeted(signal)` is for scripts and tests that call an adapter directly.
- `Admitted.priced` writes a request's known cost to its hold at once, so the next `admit` of the same attempt, and boot reconciliation after a crash, count it. An attempt with one request settles it at the usage event's cost. With several, each settles at the cost its adapter reported through `Admitted.priced`, or at its reservation when it has none, so an unknown continuation never erases the known cost of the responses before it. The usage event's cost stays unknown (R17).
- Neither cap holds a `wrap_up` call, and a tutor turn that a cap holds when its only allowed move is `wrap_up` gets code's wrap-up line instead, so a learner can always finish and save. The stop switch still holds both, and a wrap-up still reserves, settles and counts.
- `memo.run` returns `RunResult<O>`, which is `Lookup<O>` or `Held` (`{ kind: "held", key, hold }`): the budget refused a request before it was sent, so nothing was stored and the key stays missing. If earlier requests of the attempt were sent, their usage event is recorded first. `lookup` never returns `held`. `appliesBefore` takes a `RunResult`.
- The scheduler reads one thing of a run's result: a `held` key is left alone for `heldRetryMs` (60 s) and one timer pumps every held key again then.
- `BudgetHold` for a cap carries `usedUp`: spend had reached that cap. `heldMessage` says "used up" only then, and otherwise "Not enough of this month's AI allowance is left for another AI step", for the per-user cap and the total alike.
- Hosted mode ignores `ELEVENLABS_API_KEY` and logs that it does, because voice is not budgeted. Local mode is unchanged.
- A held tutor turn streams `turn_held` with its `BudgetHold` and ends; the learner's turn stays stored, so a resend continues it. `GET /usage` carries the user's `allowance` (null in replay mode). `src/shared/allowance.ts` holds the words a learner reads. Hosted, the usage page shows only the allowance; the tables by cost kind and purpose are local only.
- `ProviderError` takes an optional `billing`. A `not_billed` failure with no usage is recorded as an estimated $0 (basis "rejected before any model ran") and settles its hold at $0.

## Working rules

- Tests go in `test/<module>.test.ts` and use `fakeTask` from `test/fakes.ts`. No live Jev or Claude call outside Derek's five approved experiments. When you write the real test for a rule, delete its `test.todo` line in `test/rules.test.ts` in the same commit.
- Pure logic goes in your module's `core.ts`. Only your module and `test/` may import it.
- To change your tables, append a migration to your own array in `MIGRATIONS` (`src/backend/migrations.ts`). Never edit an applied migration; `openDb` refuses one whose text changed. That array is the only line range of a kernel file you may touch. `migrations.ts` is at the 1000-line lint limit, so the record's `004-user-id` text lives in `migrations-record.ts` and is the last entry of the `record` array.
- Write SQL only against tables your row lists. `test/boundaries.test.ts` fails otherwise.
- Quote Derek's rules as `Rn: "<exact text>"` wherever code enforces one. `test/rules.test.ts` fails on any wording that differs from `docs/flows/after-class.md`.
- Every provider call is `memo.run(task, input)`. Derivations read `memo.lookup` and apply results only through `appliesBefore(lookup, cutoff)`.

## The pump

- A capture is live while it can have demand. Every capture is live at boot. A pump that finds no demand in a capture drops it from its user's live set, and ingest, retry, stop early and a deletion by the user bring it back. A pump derives only live captures, so what one uploaded fact costs does not grow with the number of stored lectures.
- An upload's pump runs at most `INGEST_PUMP_MS` (100 ms) after the first fact of a burst, after the reply. A job that stops being demanded is aborted that much later than before. Stop early and retry still pump at once (R8). Results still apply only through `appliesBefore`.
- A capture that leaves the live set remembers the keys (`Dep`, `src/backend/deps.ts`) its last derivation read, and a write wakes every sleeper that read one of the keys it reports. The stores do the recording, where they read. `lookup` reports the memo key. Evidence reports `capture:<id>` for a capture's own facts, `source:<id>` for each source a bundle gathers (a bundle reads the facts of every capture that watched the source), and `removals` for the user's deletions. Preparation reports the frozen input slot it reads (`slot:<kind>:<subject>`), which every capture reaching the same claim or concept shares. Writes report what they changed: memo (a hit, a terminal failure, a cleared failure), an upload (its capture and every source the capture has facts about), the user's deletion and the retention sweep (`removals`), and a first freeze of a slot. A new cross-capture read needs a key at its read and at its write, and `test/main.test.ts` checks that no sleeping capture has demand after each step of a scenario that shares a video.
- A write reports through `db.afterCommit`, which runs after the outermost transaction commits and drops the notification when that transaction, or the savepoint it was registered in, rolls back.
- A capture's running jobs are demanded while they run, so a capture with no demand has none to abort. The pass that finds no demand aborts what no longer is demanded.
- A scheduler pass reads demand again after it aborts anything, because an abort listener runs synchronously and can change what is demanded.
- Evidence drops only the written capture's cached projection on an upload.

## Users in the providers module

- `createMemo`, `createLedger` and `createVoice` take a `UserDb` and read and write only its `userId`'s rows. A memo is per user: its rows are keyed by (`user_id`, `key`), and the key stays a hash of the call alone. A `MemoKey` is therefore unique only within one user, so a module that stores one beside its own rows reads it back through that user's memo.
- `memo.run` takes an optional `captureId`, stored on the call's usage events. `main.ts` passes it for boundary calls; the other callers do not know the capture yet and leave `usage_events.capture_id` null.

## Users in segmentation

- `createSegmentation` takes a `UserDb` and reads and writes only its `userId`'s chunk revisions. A chunk id derives from the capture id and a revision id from the chunk and its material, so two users who hold one capture id make identical ids. The table is keyed by (`user_id`, `id`) and unique on (`user_id`, `chunk_id`, `revision_no`), and `supersedes` is a composite foreign key to the same user's revision. The derivations are unchanged, so every stored id, scope and memo key stays valid.
- `POST /captures/:captureId/retry-preparation` is guarded at the `http.ts` capture boundary through `EvidenceStore.holdsCapture`, like every other capture-scoped route. Segmentation has no ownership check of its own.

## Users in preparation

- `createPreparation` takes a `UserDb`, and every statement carries its `userId`. Claim ids hash the interpretation's memo key, concept ids hash a label, and a frozen input's subject is a chunk revision, claim or concept id, so two users who watch one lecture derive identical ids. All four tables therefore key by (`user_id`, id) and the derivations stay.
- A frozen input (`prep_inputs`, one row per user, kind and subject) is first-writer-wins per user. Another user's row never holds a slot, so one user's job is never dropped as outdated because the other froze a different input, and a stop early or retry fact (`prep_controls`) reaches only its own user's derivation (R8).
- `prep_inputs.memo_key` is read back through the same user's memo. It has no foreign key to `memo_inputs`, because a frozen input is written before the job's memo row exists.
- Preparation has no route of its own that takes an id. `retry-preparation` is guarded through `Segmentation.heldByAnotherUser`.

## Wire contract

`ROUTES` in `src/shared/wire.ts` is the only list of HTTP routes. The extension worker and `createApi` call nothing outside it, and `http.ts` serves exactly it. Each entry has a method, a `:param` path, optional query and request schemas, and a reply (`json` schema, `ndjson` event, `jpeg`, or `empty` for 204). Add a route there first; `test/wire.test.ts` fails if a client calls one that is missing.

- `clientSeq` starts at 0 per capture and rises by 1 per fact. `POST /ingest` is idempotent on (captureId, clientSeq) and returns `ackedThroughSeq`, the highest contiguous clientSeq stored, or -1 before clientSeq 0 has arrived.
- `POST /captures/:captureId/invite` returns the new `InviteState`. The extension reads it back; the app ignores it.
- The record commands (`PATCH`/`DELETE` notes, link decisions, dispute resolution, override, evidence delete) reply 204 with no body.
- `POST /captures/:captureId/retry-preparation` (`retryPreparation`) takes no body and replies 204. It re-queues the capture's chunks that are unfinished or have no supported claim; the app's "Check again" is its caller.
- `POST /reviews/:reviewId/turns` runs one turn per review: a second post with a different `turnId` while one runs answers 409; the same `turnId` joins and replays. A stream still open after 5 minutes ends with `turn_failed` (retryable) while the turn finishes; its resend replays it.
- `ReviewView.saved` is `LearningRecord.saveState(reviewId)`: `saved` once `saved_reviews` has the review, `save_pending` after a failed save with none since (`save_failures`, survives a restart), else `unsaved`.
- `GET /reviews/:reviewId/diagrams` lists every topic of the review's frozen scope with its frame and where its summary stands (`no_claims`, `not_requested`, `preparing`, `ready`, `failed`) and makes no model call. `POST /reviews/:reviewId/diagrams/:topicId` starts that topic's summary (one `diagram_summary` Claude call per topic and evidence set, memoized) and answers with the same shape; asking again after `failed` retries. R19 is enforced in the task and again when the summary is read.
- Ingest is bounded at the boundary. A frame is at most `MAX_FRAME_BYTES` (1 MiB, wire schema), its JPEG header must agree with the width and height its fact declares, and a request body is at most `MAX_BODY_BYTES` (8 MiB, repeated as `request_body` in the Caddyfile). `ingest` throws `IngestRefused` before writing a file when a batch that adds bytes would take the user's stored bytes (UTF-8 bytes of fact rows and snapshot text, `frames.bytes`, and `evidence_snapshots.bytes` of a snapshot whose raw frame row is gone) past `AFTERCLASS_USER_QUOTA_MB` (default 512, answered 507, not retried by the extension) or leave the data volume below `AFTERCLASS_MIN_FREE_MB` (default 2048, answered 503 with `Retry-After`, retried). 0 turns a limit off. A batch with nothing new is a heartbeat: it writes no row, not even the capture's owner, and is not metered. Frames stored before migration 005 and snapshots before 006 count 0 bytes. The extension holds a capture's uploads for 15 minutes after a 507 and for a 503's `Retry-After`, on every trigger and across a worker restart (`uploadGates` in `chrome.storage.local`), until the learner resumes the capture.
- Evidence is per user. `createEvidence` takes a `UserDb`, and every query carries its `userId`. `EvidenceStore` gains `holdsCapture(captureId)`, `capturedByAnotherUser(captureId)` and `heldByAnotherUser(ids)`. `http.ts` checks `holdsCapture` once, before the route switch, so every route with a `:captureId` path parameter, and `GET /evidence?captureId=`, answers 404 for a capture id the caller does not hold, whether nobody holds it or another user does. `ingest` is the exception, because a device creates a capture by ingesting into a new id, and it keeps `capturedByAnotherUser`. A frame id nobody holds keeps its old answer. `ingest` throws `RangeError` for a capture id another user already holds. The first ingest records the owner in `capture_owners` inside its transaction, and expiry never deletes it. New frame and snapshot files live under a per-user directory, and no file is unlinked while any row still points at it, so a capture id and the frame ids and file paths derived from it belong to one user. Passage evidence ids come from the transcript and are shared, so `evidence_snapshots`, `evidence_deletions` and `frames` key by `(user_id, evidence_id)`.
- Reviews are per user. `createReviews` takes a `UserDb`, and every query carries its `userId`. A review id is minted by the app and belongs to the first user that starts it: `reviews.id` stays the key, `reviews` never deletes a row, and `start` throws `RangeError` for an id another user holds, which `http.ts` answers with 404 (as it does for `GET /reviews/:reviewId`, the turn, save and record routes). Tutor and code turn ids, notes and observations derive from the review id, so they stay one user's. A turn id is minted by the app too and keys by (`user_id`, `id`) with a composite foreign key to the user's own review, so the same turn id from two users is two turns: neither replays, joins or blocks the other. The in-flight guard in `http.ts` is keyed by review id, which is unique across users. The R16 triggers on `capture_facts` and `frames` hold only for a review of the same user.
- The record is per user. `createRecord` takes a `UserDb`, and every query carries its `userId`. Every key leads with `user_id`, because a link id derives from concept ids that every user who watches a lecture shares; note and observation ids derive from a review id, which is one user's. `notes`, `observations` and `link_suggestions` carry an `ord` column (one past the user's highest) and are read in that order, in place of `rowid`. `http.ts` answers 404 for a note, link or observation the caller does not hold, and `GET /record?reviewId=` for a review only another user holds; an id nobody holds keeps its old answer (404 for a command, an empty view for the query). The R16 triggers match the same user: a note holds only its own user's snapshot of an evidence id both users hold, a tombstone releases only its maker's, and a review is saved by its own user's `saved_reviews` row.
- `test/ownership.test.ts` is plan step 4. `CASES` has an entry for every route in `ROUTES`, so a new route fails typecheck until it says how a second user is refused (404, or the documented no-op: evidence ids and material another user holds read as an empty bundle). A route with a path parameter may not be marked as taking no id.
- A `Material` crosses JSON as `Material.canonical` rows. Use `encodeMaterial` and `decodeMaterial`; the `GET /evidence?material=` value is `encodeURIComponent(encodeMaterial(m))`.
- Response schemas live in `wire.ts`. `src/app/decode.ts` re-exports them as aliases.
- Frozen exports that changed after the Tutor and record row was written: `RecordBundle.observations` carries `assessable` per observation, and `clampStatus(proposed, facts, dispute, assessable)` takes a fourth argument; when a thread's claim is not assessable at save, the status is `not_assessed` (R3).

## Hosted sign-in

- `AFTERCLASS_AUTH=clerk` starts `mainHosted`. Unset, `main` runs the local app exactly as before: pairing token, Host check, one local user.
- `users` gains `auth_provider` and `auth_subject` (kernel `003-identity`), unique together and null for the local user. `userForIdentity` returns the row for a Clerk subject and creates it on first sign-in. Its id is random.
- `ServeOptions` takes either `modules` with `auth` (local) or `modulesFor` with `hosted` (hosted). In hosted mode `HostedAuth.userFor` verifies the bearer token (`src/backend/clerk.ts`) and names the user, and `modulesFor` gives that user's modules, which `main.ts` builds once per user on that user's `UserDb`.
- The scheduler is shared across users. Its work item keys add the user id to the memo key, because two users' identical calls have the same memo key.
- In the app, `followAccount` (`src/app/account.ts`) gives each signed-in account its own services and disposes them when the account changes. Unsent turns live in one IndexedDB database per account, and the app deletes every other account's database. `createApi` takes the account's lifetime as `signal`.

## Connected browsers

- Hosted only. The extension connects with a one-time code from `/app/connect-extension` and then sends a device token. `docs/architecture/hosted-sign-in.md` has the flow.
- `Route.bearer` names the tokens hosted mode accepts on each route: `session` from the app, `device` from the extension, or none for `exchangeConnectCode`, whose code is the credential. A device token reaches only `ingest` and `answerInvite`, and only from the pinned extension's Origin. Locally the pairing token still reaches every route, and the four device routes answer 501.
- `devices.ts` is a kernel file: it owns `devices` and `connect_codes` (kernel `004-devices`), stores only SHA-256 hashes, and is their only writer. It takes a `Db`, not a `UserDb`, because a code or a token is how the user is found. `revoke` and `list` take the caller's user id, and another user's device answers as unknown. A token unused for `DEVICE_IDLE_TTL_MS` (90 days) is refused, and a Connect past `MAX_DEVICES_PER_USER` (10 live devices) revokes the least recently used one.
